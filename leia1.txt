# Diretriz de execução — não confundir prova de conceito com solução final

O plano acima está aprovado como direção de investigação, mas quero ajustar a forma de execução.

## Regra principal

Não trate a arquitetura GPU como solução comprovada antes dos benchmarks.

A sequência correta é:

```text
MEDIR
  ↓
IDENTIFICAR GARGALO
  ↓
CORRIGIR INFRA
  ↓
CRIAR PROTÓTIPO GPU
  ↓
COMPARAR
  ↓
VALIDAR ESCALA
  ↓
SÓ ENTÃO MIGRAR
```

Não pule etapas.

---

## 1. Primeiro faça somente o Passo 0

Antes de alterar Fire Ball ou criar qualquer renderer novo, rode os benchmarks já existentes.

Não crie uma infraestrutura paralela de benchmark se a existente realmente cobre o cenário.

Para Fire Ball:

```text
1
5
10
20
30
```

E depois o combo.

Para cada cenário registre, quando disponível:

```text
FPS
frame time
JS
style
layout
paint
raster
composite
GPU
DOM nodes
CSS animations
```

O objetivo dessa primeira etapa é responder:

> Qual parte da Fire Ball realmente domina o custo quando a quantidade de instâncias cresce?

Não basta dizer "ela tem 118 DOMs".

---

## 2. Fire Wall deve ser investigado separadamente

Execute o harness existente com 30 células e faça uma matriz de ablação:

```text
baseline

- embers
- glow
- licks
- smoke

glow only
smoke only
embers only
licks only

glow + smoke
glow + embers
smoke + embers
etc., se necessário
```

Quero descobrir especificamente de onde vêm os ~39 ms.

Não assuma:

> "é compositor porque tem blur"

Isso é uma hipótese.

O resultado deve dizer qual combinação explica a maior parte do custo.

Se o custo continuar mesmo com todos os elementos suspeitos removidos, investigue a próxima camada do pipeline.

---

## 3. Damage numbers

Faça o teste de text-shadow separadamente.

Não remova definitivamente.

Compare:

```text
text-shadow ON
text-shadow OFF
```

com quantidade alta de números simultâneos.

Além da performance, confira visualmente a legibilidade.

---

# 4. Só depois faça os fixes do GPU renderer

Os dois fixes descritos são aceitáveis porque são defeitos objetivos:

### BeamRenderer

Eliminar allocations recorrentes por frame.

### Sprite/Particle

Conectar corretamente:

```text
payload.color
payload.opacity
```

ao atributo GPU.

Depois rode typecheck/testes.

Não misture esses fixes com a migração da Fire Ball na mesma mudança sem conseguir identificar qual alteração produziu qual resultado.

---

# 5. Cuidado especial com LOD/Budget

O LOD e o Budget já existem.

Não reescreva o sistema.

Primeiro descubra:

```text
onde o resultado de computeBudgetPressure()
deveria entrar no pipeline atual.
```

Faça a menor alteração possível para ativá-lo.

Também não escolha thresholds arbitrários apenas para produzir FPS melhor.

Os thresholds precisam ser derivados dos dados.

E o comportamento deve ser estável.

Evite:

```text
frame ruim
→ reduz VFX

frame bom
→ aumenta VFX

frame ruim
→ reduz

frame bom
→ aumenta
```

a cada frame.

Use histerese/debounce conforme necessário.

---

# 6. Fire Ball GPU deve ser um PROTÓTIPO, não uma migração irreversível

Esse é um ponto importante.

A Fire Ball atual deve continuar disponível como baseline.

Crie uma forma clara de alternar:

```text
Fire Ball DOM
vs
Fire Ball GPU
```

sem alterar gameplay.

Por exemplo, através de uma flag de benchmark/dev.

Assim podemos executar exatamente o mesmo cenário com:

```text
renderer = DOM
```

e:

```text
renderer = GPU
```

usando a mesma skill, mesmos jogadores, mesmos casts e mesmos tempos.

---

# 7. Não tente copiar 118 elementos DOM literalmente

A versão GPU não precisa ter:

```text
8 ember
6 sparks
5 flames
5 forward
...
```

como entidades equivalentes individuais.

O objetivo é preservar a **linguagem visual**, não a implementação.

Se 20 partículas GPU produzem visualmente o mesmo resultado que 80 DOM particles, prefira 20.

Se precisar de 200 GPU particles para preservar o visual, tudo bem.

O benchmark deve mostrar o custo.

---

# 8. O renderer GPU deve continuar genérico

Não coloque lógica específica de Fire Ball dentro de:

```text
SpriteRenderer
ParticleRenderer
BeamRenderer
```

Evite coisas como:

```text
if skill === FIRE_BALL
```

O renderer deve receber dados genéricos.

Fire Ball deve ser uma composição de primitivas existentes:

```text
particle
sprite
ring
trail
```

e parâmetros.

---

# 9. Trail

Antes de implementar um sistema sofisticado de trail, faça a versão mínima.

A pergunta é:

> conseguimos reproduzir o rastro atual com instâncias GPU sem criar DOM por segmento?

Se sim, ótimo.

Não crie um renderer gigantesco de trail se um conjunto de instâncias billboard resolver.

Mas tome cuidado para não atualizar todos os slots de todas as skills a cada frame se eles estiverem fora da câmera ou em LOD baixo.

O culling/LOD precisa chegar até a simulação.

---

# 10. Muito importante: separar SIMULAÇÃO de RENDERIZAÇÃO

Quero que a arquitetura final mantenha esta separação:

```text
Gameplay
   ↓
VFX event
   ↓
VFX instance
   ↓
simulation state
   ↓
renderer
```

O renderer não deve possuir a lógica da skill.

E a skill não deve conhecer DOM/GPU.

---

# 11. Culling deve impedir trabalho, não apenas desenho

O sistema já possui culling por frustum.

Verifique se um VFX fora da câmera deixa de:

* renderizar;
* simular partículas desnecessariamente;
* atualizar buffers;
* atualizar trails;
* executar animações caras.

Se atualmente o culling só impede desenho mas continua fazendo toda a simulação, considere isso uma oportunidade de otimização.

Mas meça antes de alterar.

---

# 12. Faça um teste de escala que realmente valide a arquitetura

Depois da Fire Ball GPU funcionar:

```text
DOM:
1 / 5 / 10 / 20 / 30 Fire Balls

GPU:
1 / 5 / 10 / 20 / 30 Fire Balls
```

Compare:

```text
FPS
frame time
CPU
GPU
DOM count
active CSS animations
particle count
draw calls
memory
GC, se mensurável
```

O dado mais importante não é apenas:

> "GPU tem FPS maior".

Quero observar a **curva de crescimento**.

Por exemplo:

```text
DOM
1 → 5 → 10 → 20 → 30
crescimento muito acentuado

GPU
1 → 5 → 10 → 20 → 30
crescimento muito menor
```

É isso que demonstrará que a arquitetura escala.

---

# 13. Depois teste o combo completo

Não declare vitória porque Fire Ball isolada ficou rápida.

Rode novamente o cenário caótico:

```text
Fire Ball
Lightning Storm
Fire Wall
Oracle
Cold Bolt
Soul Strike
```

em:

```text
1
5
10
20
30
```

Compare com o baseline anterior.

Relate separadamente:

```text
Fire Ball improvement
+
overall combo improvement
```

Se Fire Ball melhorar muito mas o combo continuar em ~1 FPS, isso é um resultado válido.

Nesse caso precisamos descobrir o próximo dominante.

Não tente mascarar isso aumentando LOD agressivamente.

---

# 14. Critério de sucesso

Considere a Fire Ball uma prova de conceito bem-sucedida somente se houver:

### Performance

A curva de custo com muitas instâncias for significativamente melhor que DOM/CSS.

### Escalabilidade

A quantidade de jogadores/efeitos puder crescer sem multiplicar o custo de renderização na mesma proporção que o DOM atual.

### Visual

A aparência continuar suficientemente próxima do estilo atual.

### Arquitetura

A mesma infraestrutura puder ser usada por outras skills sem código específico de Fire Ball.

### Gameplay

Zero alteração em:

```text
damage
cooldown
target
duration
hit detection
network synchronization
skill logic
```

---

# 15. Se a aproximação visual ficar ruim

NÃO descarte automaticamente a arquitetura.

Separe as duas conclusões:

```text
GPU architecture:
VALIDADA / NÃO VALIDADA

Fire Ball visual:
ACEITÁVEL / PRECISA DE ARTE MELHOR
```

É perfeitamente válido concluir:

> "A arquitetura GPU escala muito melhor, mas a representação procedural atual não reproduz suficientemente bem a arte."

Nesse caso, podemos posteriormente introduzir atlas/texturas ou outras técnicas sem abandonar a arquitetura.

---

# 16. Resultado esperado da rodada

No final, quero um relatório objetivo com:

```text
1. Gargalo real da Fire Ball
2. Gargalo real do Fire Wall
3. Resultado do text-shadow
4. Correções feitas no GPU renderer
5. Resultado do LOD/Budget
6. Resultado Fire Ball DOM vs GPU
7. DOM count antes/depois
8. FPS/frame time antes/depois
9. Resultado do combo
10. Diferença visual
11. Próximo gargalo identificado
12. Próxima skill recomendada para migração
```

Não quero que a conclusão seja simplesmente:

> "GPU é melhor."

Quero saber **quanto melhor, em qual cenário, por qual motivo e onde o próximo gargalo passa a estar**.

A prioridade é construir uma arquitetura de VFX que continue funcionando quando o jogo tiver dezenas de jogadores usando skills simultaneamente — não apenas fazer uma Fire Ball específica ficar rápida.
