### Objetivo desta etapa

Integrar o Writer existente ao fluxo real de edição de NPCs no Admin/API.

O objetivo é fazer uma edição realizada pelo painel chegar ao `planNpcWrite` e, quando aprovada pelo Writer, alterar o `.txt` correspondente no rAthena de forma segura.

### Regras obrigatórias

1. **Não ampliar as capacidades do Writer nesta etapa.**

   * Não liberar edição direta de `legacyScript`.
   * Não liberar adição, remoção ou reordenação de nós.
   * Não liberar adição ou remoção de handlers inteiros.
   * Não criar novas regras de reconstrução.
   * Usar exatamente as capacidades que o Writer já possui e que já foram testadas.

2. **Não fazer bypass do Writer.**

   * Nenhuma edição deve escrever diretamente no `.txt`.
   * Toda escrita deve passar pelas validações e recusas existentes do Writer.

3. **Não quebrar o CRUD existente de NPCs.**

   * Antes de alterar qualquer fluxo, mapear exatamente como GET/PUT funcionam hoje.
   * Identificar quais dados o Admin envia e quais dados o Writer precisa.
   * Não assumir que `legacyRef` sozinho é suficiente sem verificar como o arquivo real pode ser localizado com segurança.

4. **Preservar o banco como fonte dos dados editados pelo Admin**, mas garantir que a escrita no `.txt` e a atualização do banco não possam ficar silenciosamente inconsistentes.

5. **Não escrever em rathena/ durante a implementação**, exceto nos testes funcionais explicitamente planejados para validar o fluxo.

### O que investigar antes de alterar código

Mapear o fluxo completo:

`NpcForm.tsx → Admin API client → PUT /npcs/:id → API route → repository → Supabase/JSON`

e determinar:

* como o NPC é carregado no Admin;
* qual representação é editada pelo formulário;
* como o `before` deve ser obtido do `.txt` real;
* como o `after` deve ser construído a partir da edição;
* como o arquivo é identificado;
* como impedir edição de um NPC caso o arquivo original tenha mudado desde o carregamento;
* como lidar com Writer recusando uma edição;
* como garantir que uma falha na escrita do `.txt` não seja apresentada ao usuário como sucesso;
* como garantir que uma atualização do banco não ocorra quando a escrita necessária no `.txt` falhar;
* como representar no Admin uma recusa do Writer e seu motivo.

### Concorrência / stale data

Verificar explicitamente o risco de:

1. Admin carrega NPC.
2. Arquivo `.txt` muda externamente.
3. Admin salva uma versão baseada no estado antigo.

A integração não deve aplicar silenciosamente uma edição contra uma versão diferente daquela carregada pelo usuário.

Se o sistema atual não possui informação suficiente para detectar isso com segurança, **não inventar uma solução silenciosa**. Identificar o bloqueio e parar para aprovação.

### Testes obrigatórios

Antes de conectar ao fluxo real, criar testes que comprovem:

* GET → edição válida → PUT → Writer aceita;
* edição recusada pelo Writer não altera `.txt`;
* erro ao localizar o `.txt` não altera o banco;
* erro de validação não altera `.txt`;
* edição válida altera somente o trecho permitido;
* conteúdo não editado continua byte-identical;
* `eventHandlers` não relacionados permanecem intactos;
* `legacyScript` vizinho permanece intacto;
* múltiplos NPCs não interferem entre si;
* concorrência/stale source é tratada explicitamente;
* resposta da API diferencia sucesso de recusa do Writer e erro operacional.

### Teste funcional

Depois dos testes unitários/integrados, usar **um NPC real em arquivo temporário**, não um `.txt` de produção do rAthena, para provar o fluxo completo:

`Admin/API → before real → after → Writer → arquivo → reparse → validação`

Somente depois dessa prova, e mediante aprovação separada, considerar um teste controlado contra um arquivo real do rAthena.

### Limites

Não fazer nesta etapa:

* redesign do `NpcSchema`;
* novo sistema de AST;
* expansão do Mapper;
* expansão do Validator;
* novas capacidades de edição do Writer;
* edição de `legacyScript`;
* criação/remoção de nós;
* criação/remoção de event handlers;
* alteração de scripts de `function script`;
* reload do servidor real;
* alteração permanente de NPC real.

### Critério de parada

Se existir qualquer decisão arquitetural não determinada pelo código existente — especialmente sobre atomicidade banco ↔ `.txt`, identificação do arquivo, concorrência ou comportamento do Admin — **não escolher arbitrariamente**.

Mapear o problema, apresentar a decisão necessária e parar.

4. resultados dos testes;
5. comportamento em caso de Writer rejection;
