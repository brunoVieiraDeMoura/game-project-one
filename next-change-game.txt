## 1. Primeiro: investigar os ACKs

A auditoria anterior encontrou:

```text
CZ.REQ_WEAR_EQUIP
CZ.REQ_TAKEOFF_EQUIP
```

e ausência de handlers para:

```text
ZC.WEAR_EQUIP_ACK 0xaa
ZC.TAKEOFF_EQUIP_ACK 0xac
```

Confirme isso diretamente no source do rAthena.

Descubra:

* estrutura exata dos packets;
* campos;
* tamanho;
* índice;
* localização;
* resultado;
* sucesso/erro;
* como o equipamento é identificado.

Não invente o formato.

Se os ACKs reais forem diferentes do que a auditoria encontrou, use o protocolo real.

### Regra

Se o protocolo não estiver suficientemente confirmado, **pare antes de implementar** e informe exatamente o que falta.

Não crie um protocolo fictício.

# 2. equipmentStore

Depois da confirmação do protocolo, crie um `equipmentStore` somente se for realmente necessário.

Ele deve ser uma projeção do estado autoritativo, não uma fonte de verdade paralela.

Quero algo conceitualmente equivalente a:

```text
rAthena
↓
gateway
↓
playerStore / equipmentStore
↓
UI
```

Nunca:

```text
double click
↓
cliente decide "equipado"
↓
UI mostra
```

antes da confirmação do servidor.

# 3. Metadata

O catálogo já possui:

```text
type
subType
locations
jobs/classes
slots
onEquip
onUnequip
onUse
```

Enquanto `InventoryItem` é muito menor.

Não copie o catálogo inteiro para cada item.

Use:

```text
InventoryItem.itemId
+
ItemCatalog[itemId]
↓
resolved metadata
```

Precisamos conseguir determinar corretamente:

* tipo;
* subtipo;
* localização;
* classe/job;
* slots;
* requisitos;
* stats;
* cards;
* refine.

Evite duplicação de dados estáticos.

---

# 4. Equipar

Manter a regra já implementada:

```text
clique único → consumível usa
double click → equipamento tenta equipar
```

Double click deve:

1. localizar item;
2. verificar se é equipamento;
3. resolver metadata;
4. verificar compatibilidade básica;
5. enviar request;
6. esperar ACK;
7. refletir resultado autoritativo.

O cliente pode bloquear requests obviamente inválidos, mas o servidor continua sendo a autoridade final.

---

# 5. Desequipar

No `alt+Q`:

```text
double click equipamento
```

deve enviar o request real.

Após ACK:

```text
equipamento removido
item retorna ao inventário
status atualizado
UI atualizada
```

Se o servidor rejeitar:

```text
equipamento permanece equipado
```

Não remover otimisticamente.

Não duplicar item.

Não perder item.

# 8. STATUS — prioridade máxima

Precisamos provar que equipamento afeta o estado real do personagem.

Teste:

```text

↓

↓

```

Depois:


Não basta mudar texto da UI.

Não calcule o status final apenas no cliente.

O valor real deve continuar vindo do servidor.

# 9. Indicador temporário de status

Implementar o requisito:

Quando equipar/desequipar um item, mostrar durante aproximadamente 10 segundos o que mudou.

Exemplo:

```text
ATK 120   ↑ +20
```

ou:

```text
ATK 100   ↓ -20
```

O fluxo correto é:

```text
status antes
↓
request
↓
ACK
↓
novo estado autoritativo
↓
diff
↓
indicador visual
```

Não mostrar o indicador como confirmado antes do ACK.

---

# 10. Delta

O delta deve ser calculado entre os valores autoritativos:

```text
delta = after - before
```

Exemplo:

```text
antes:
ATK = 100

depois:
ATK = 120

delta:
+20
```

O cálculo do delta serve apenas para o indicador visual.

Não use:

```ts
newAtk = oldAtk + item.atk
```

como fonte do status real.

---

# 11. Vários status

Se o equipamento modificar vários atributos:

```text
ATK 120   ↑ +20
DEF 80    ↑ +10
HP 1500   ↑ +200
```

mostrar todos os que realmente mudaram.

Não mostrar:

```text
+0
```

nem valores que não mudaram.

O indicador dura ~10 segundos e desaparece.

Se outra troca acontecer antes do timer terminar, atualizar/reiniciar o indicador de forma consistente.


Não criar infraestrutura complexa sem necessidade.
